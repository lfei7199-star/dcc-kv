> ## ⚠️ 勘误（2026-09-30 追加）
>
> 本报告中标为 **`budget_0.5` / `budget_0.25`** 的臂**标签是错的**：
> 它们传的是 `compaction_mode="identity"`，而该模式在 `apply_kv_budget` 里是
> 「**裁剪策略 = 恒等**」⇒ **什么都没裁，实际等于 `dense`**。
> 实测（`verify_compression_effective.py`，S=4096、源段 3072、预算 25%）：
> `identity` 裁后 cache 长度仍是 **3072**；`topk_rms`/`random`/`stride` 才裁到 **768**。
>
> ⇒ 报告中这些行的 `acc=1.0000` **不构成"压缩后仍正确"的证据**；
> 那一批数字测的是未压缩路径。有效模式只有
> `topk_rms` / `topk_norm` / `random` / `stride`。
>
> 修正后的结果、以及对压缩**敏感**的新评测集，见
> **`reports/2026-09-30-评测集与压缩敏感性验证.md`**。

## 一、结论

**不需要真实 GPU。** 在 CPU + 真预训练权重上，链路已完整跑通并产出输入输出。

论证的层次划分是关键——"用模型完成输入输出"有四种强弱不同的含义：

| 档 | 含义 | 需要 GPU 吗 | 本次状态 |
|---|---|---|---|
| ① | 形状/接口正确（forward 不炸、shape 对） | ❌ | ✅ 已证 |
| ② | **能完成输入输出**（真权重 + 走完评测路径 + 出逐样本结果） | ❌ | ✅ **本次证毕** |
| ③ | 答得**对**（任务质量） | ❌（但需真权重） | ⚠️ 见下「证据边界」 |
| ④ | 比共享压缩**好**（H2 的 1.5pp） | ✅ **必须真多卡** | ❌ 无卡 |

**② 已在两个层次上证毕**：
- 基础层：真权重四臂端到端（SmolLM2 / Qwen，含跨族）
- 长文本层：**4096 token** 长文本 + 源端切 2/4 段 + 压缩（2026-09-30）

**为什么 ② 不需要 GPU**：GPU 解决的是"跑得动 8B"，不是"能不能测"。
评测路径（`load_model` → `evaluate` → `score_choices` → 长度归一平均 logprob）
本身与设备无关；`load_model` 的 `device` 参数可直接传 `"cpu"`。

## 三、实测结果

### 3.1 四个臂，同一入口，同构字段

| 臂 | 走什么路径 | SmolLM2-135M | Qwen2.5-0.5B |
|---|---|---|---|
| `dense` | 精确注意力，无压缩 | acc=1.0000 | acc=1.0000 |
| `budget_0.5` ⚠️ | **实为未压缩**（等同 dense，见勘误） | acc=1.0000 | acc=1.0000 |
| `budget_0.25` ⚠️ | **实为未压缩**（等同 dense，见勘误） | acc=1.0000 | acc=1.0000 |
| `hook_dcc` | **钩子**：源端切分 W=2 + 目的端条件化 + 紧凑 KV 注意力 | acc=1.0000 | acc=1.0000 |

四臂共用 `evaluate` 入口，返回 `accuracy` / `by_task` / `by_length` /
`per_sample` / `keys` —— 结构相同，因此**可配对比较**（H2 的 CI 所需格式）。

### 3.2 跨族：钩子未改一行代码即挂上 Qwen

```
arch=Qwen2ForCausalLM   attn=Qwen2Attention   layers=24   kv_heads=2   heads=14
[臂4 钩子W=2]  acc=1.0000  per_sample=[1, 1]
```

原预期「Qwen 需薄适配器」，**实测不需要**：`Qwen2Attention` 同样具备
`layer_idx` 属性，GQA 映射（`h // (H_q/H_kv)`）也走同一条路径。
⚠️ 但这是 **0.5B**，不能据此推断 72B 同样可行。

### 3.3 三条"主动拒绝"——设计而非缺陷

调试过程中钩子**连续三次拒绝执行**，每次都给出具体理由，且都是保护性行为：

| 传参 | 钩子的回应 |
|---|---|
| `dest_fraction=0.0` | 拒绝：目的端本地段是**条件化 query 的唯一合法来源**；用被打分的 continuation 去条件化**等于让压缩看见答案** |
| `budget_ratio` 两处都传 | 拒绝：不让"预算到底按谁算"变成猜 |
| `compaction_mode='build'` | 拒绝：那是 `apply_kv_budget` 的旋钮，与钩子抢同一份 cache |

**这对外说明时是加分项**：这套代码宁可报错也不静默降级，不会给出
"看起来正常、实际无意义"的数字。

### 3.4 计时：钩子路径显著慢于 dense（实现差距，非机制收益/损失）

| 臂 | SmolLM2 (6 条) | Qwen (6 条) |
|---|---|---|
| `dense` | 6.6s | 16.3s |
| `budget_0.5` ⚠️ | 6.4s | 15.8s |
| `budget_0.25` ⚠️ | 6.5s | 15.7s |
| `hook_dcc` | **99.3s**（15.1×） | **68.5s**（4.2×） |

原因：`dense` 走 SDPA 融合核，`hook_dcc` 走 `attention_kernel` 的**显式核**，
且含构造代价（`build_compact_kv`）。这正是代码里说的
`prefill_speedup_native` —— **含实现差距，不得当作机制收益引用**。
H2 消费的是 `prefill_speedup_kernel_matched`（两臂同核），本表**没有**测那个。

---

### 3.5 4k token 长文本 + 切分（2026-09-30 追加）

评测集**按 token 精确构造**（非按字符估）：实测 `[4096, 4096, 4095, 4096]`，
占 Qwen2.5-0.5B 上下文窗口（32768）的 **12.5%**。

| 臂 | acc | per_sample | 耗时 |
|---|---|---|---|
| `dense` | 1.0000 | [1,1,1,1] | 126.1s |
| `budget_0.5` ⚠️ | 1.0000 | [1,1,1,1] | 98.2s |
| **`hook_dcc_W2`**（源端切 2 段） | 1.0000 | [1,1,1,1] | 216.7s |
| **`hook_dcc_W4`**（源端切 4 段） | 1.0000 | [1,1,1,1] | 214.3s |

四臂 `per_sample` **逐位相同**（不一致样本 = 0）。

⚠️ **`W=4` 比 `W=2` 略快（214.3s vs 216.7s）**，与内存账一致：切得越细，
每片注意力矩阵越小（O((S/W)²)），矩阵收益超过构造代价增量。
**但这不是性能主张**——单次测量、单卡模拟、且含实现差距。

⚠️ 同样地，四臂全对是**天花板效应**，不是"精度不降"（见 §4.1）。

## 四、证据边界（必须与结论同时声明）

### 4.1 本次**不能**证明"压缩不掉精度"

四臂全部 `acc=1.0000`，**看起来像"压缩不掉点"，实际是零区分度 + 天花板效应**：

```
参照臂（dense）准确率 = 1.0000   ← 已满分，只能测出下降、测不出提升
配对不一致对总数 = 0             ← 配对检验（McNemar）功效为零
```

即：连参照臂都没有留出任何可退化的空间。本批样本**只能**支持
"链路跑通、压缩后仍能产出答案"，**不能**支持"精度不降"。

要把后者变成可判，至少需要：
- 样本量从 6 提到 ≥ 每点 10 次 run × 多条样本（`e6_main_table.py` 的报告规范）
- 参照臂**不撞天花板**（题目难度要够，dense 不能满分）
- 真多卡（否则 H2 的质量差恒 ≈ 0）

### 4.2 逐条边界

1. **无 GPU 产物**：`results/gpu/` 只有 `e8_cpu_reduced`，
   `authoritative: false`、`device: "cpu"`。
2. **H2 的 1.5pp 不可判**：单卡模拟下 `dcc_kv` 与 `kv_budget_shared`
   数值不可区分（`conditionalization_marginal_available=False`，
   见 `attention_hook.py:574`）。本条是**结构性**的，非数据不足。
3. **模型规模远小于论文选型**：论文用 Llama-3.1-8B/70B、Qwen2.5-72B、
   Mistral-7B；本次用 135M / 0.5B。跨族适配的结论**不可外推到 72B**。
4. **上下文长度**：本次已做到 **4096 token**（占 Qwen2.5-0.5B 窗口 12.5%），
   仍远短于论文目标 32k。16k/32k 在本机**不可行**——不是慢，是内存先崩
   （实测 16k 要 9.0 GB、32k 要 31.8 GB，直接 OOM）；
   且 SmolLM2-135M 的 `max_position_embeddings` 只有 8192。
   详见 `reports/2026-09-30-长文本长度档决策记录.md`。
5. **压缩机制非原创**：选键 / β 系数 / V 回归源自 MIT CSAIL Attention
   Matching（arXiv 2602.16284），对外须声明。
6. **`fastkv_official` / `ring` / `apb` 三个基线被阻断**
   （`e6_main_table.py --plan` 输出 3/6 被阻断），不得声称已与它们对比。

## 六、一句话总结（可直接引用）

> 在 CPU + 真预训练权重（SmolLM2-135M / Qwen2.5-0.5B）上，
> DCC-KV 的完整链路——源端切分、目的端条件化、紧凑 KV 注意力、评测打分——
> 已端到端跑通并产出逐样本结果，**4k token 长文本上源端切 2 段与 4 段均通过**，
> 且钩子**未改一行代码**即挂上跨族的 `Qwen2Attention`。
> **这是接口与链路的可执行性证据，不是任务质量证据。**
> 单卡下 `dcc_kv` 与共享压缩数值不可区分，故 H2 的质量主张仍需真实多卡。
>
> 附带一条**可行性论据**：32k 单卡物理装不下——实测 OOM 要分配 31.8 GB；
> 切 8 片后每片 604 MB（注意力矩阵 O(S²) ⇒ 切分省 **W² 倍**）。
> 解析式与实测 OOM 报错**逐位相同**（9,663,676,416 B @ S=16384）。
