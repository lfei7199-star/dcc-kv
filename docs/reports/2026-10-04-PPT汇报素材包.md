## 2. 背景：这道题难在哪（1–2 页）

### 2.1 项目要解决什么

长上下文推理中，KV Cache 随序列长度**线性膨胀**，是显存与延迟的主要瓶颈。
本项目的思路是：**把源序列切分到多个设备，每段独立压缩，再归并**。

### 2.2 三类工作，逐个说清定位

| 工作 | 性质 | 对外能否主张 |
|---|---|---|
| 压缩机制（选键 / β 系数 / V 回归） | **借来的** —— 源自 MIT CSAIL Attention Matching（arXiv 2602.16284） | 🔴 **必须声明非本项目原创** |
| 异步 All-to-Allv + 顺序无关 Online Softmax 归并 | **本项目原创** | 可主张机制设计 |
| 评测方法论（量具判据） | 本阶段新增 | 可主张（本汇报重点之一） |

### 2.3 本阶段要回答的两个问题

1. **链路能不能跑通？**（真权重、真长文本、真切分，不靠"看起来能跑"）
2. **如果跑通了，测得出来的结论可信吗？**（评测集本身有没有资格作证）

> 💡 制作方注意：第 2 条是本次汇报区别于普通工程汇报的关键 —— 它对应 §6 整节。

## 4. 成果一、二：链路可执行性（2–3 页）

### 4.1 真权重端到端（基础层）

**配置**：CPU，无 CUDA；**真预训练 + 指令微调权重**（非随机权重）；float32；`attn_implementation="eager"`。

| 臂 | 走什么路径 | SmolLM2-135M | Qwen2.5-0.5B |
|---|---|---|---|
| `dense` | 精确注意力，无压缩 | acc = 1.0000 | acc = 1.0000 |
| `budget_0.5` ⚠️ | **实为未压缩**（见 §7 勘误） | 1.0000 | 1.0000 |
| `budget_0.25` ⚠️ | **实为未压缩**（见 §7 勘误） | 1.0000 | 1.0000 |
| `hook_dcc` | 源端切分 W=2 + 目的端条件化 + 紧凑 KV | 1.0000 | 1.0000 |

**4k token 长文本层**（Qwen2.5-0.5B，token 数精确构造 `[4096, 4096, 4095, 4096]`）：

| 臂 | acc | 耗时 |
|---|---|---|
| `dense` | 1.0000 | 126.1 s |
| `hook_dcc_W2`（源端切 2 段） | **1.0000** | 216.7 s |
| `hook_dcc_W4`（源端切 4 段） | **1.0000** | 214.3 s |

> 🔴 **两处红线（引用时必须带上）**：
> 1. 四臂全对是**天花板效应**（参照臂已满分，测不出提升），**不能**读成"压缩不掉精度"。
> 2. `hook_dcc` 的耗时**含实现差距**（dense 走 SDPA 融合核，hook 走显式核），
>    **不是**压缩带来的收益或损失，**禁止**当作性能数字引用。

### 4.2 跨族挂载（这一页很适合做成"一张图 + 一句结论"）

**原预期**：Qwen 需要写一个薄适配器。
**实测结果**：**不需要** —— 钩子未改一行代码即挂上。

```
arch = Qwen2ForCausalLM    attn = Qwen2Attention
layers = 24    kv_heads = 2    heads = 14
[臂4 钩子 W=2]    acc = 1.0000    per_sample = [1, 1]
```

原因：`Qwen2Attention` 同样具备 `layer_idx` 属性，GQA 映射走同一条路径。

> 🔴 **红线**：这是 **0.5B** 模型，**不可**外推为"72B 同样可行"。

### 4.3 附带证据：代码"宁可报错也不静默降级"

调试中钩子**连续三次拒绝执行**，每次都给出具体理由 —— 这是设计而非缺陷，
**对外说明时是加分项**：

| 传入 | 钩子的回应（理由） |
|---|---|
| `dest_fraction=0.0` | 拒绝：目的端本地段是条件化 query 的**唯一合法来源**；用被打分的 continuation 去条件化**等于让压缩看见答案** |
| `budget_ratio` 两处都传 | 拒绝：不让"预算到底按谁算"变成猜 |
| `compaction_mode='build'` | 拒绝：那是另一处的旋钮，与钩子抢同一份 cache |

## 5. 为什么核心质量主张必须真多卡（2 页，**本次汇报的关键页**）

### 5.1 问题

项目要主张的 H2 是**三条同时成立**，不是一条线：

```
H2 = ① 与 dense 非劣（quality_comparable）
     ② 相对 shared 压缩的质量提升 ≥ 1.5 pp
     ③ 同核 prefill 加速 ≥ 1.10×
```

### 5.2 结论：第 ② 条在本机**结构上**测不出

**不是"还没跑"，而是"当前配置下这两个量在结构上就是同一个东西"**：

- 现在把源序列切成 W 段，是在**单进程 / 单卡**内模拟 W 个源端设备；
- 「逐边条件化」的价值来自**每条边看到的目的端 query 不同**；
- 单卡模拟下所有源段看到的是**同一批** query
  ⇒ `dcc_kv` 与 `kv_budget_shared` **数值不可区分**
  ⇒ 质量差 **恒 ≈ 0** ⇒ **1.5pp 不可能出现**。

**这一条是仓库自身的声明，且有代码守卫**（不是推断）：

| 位置 | 内容 |
|---|---|
| `src/distributed/attention_hook.py` 模块文档第 9 条 | 单卡下所有段看到同一批 query ⇒ 数值上仍不可区分 |
| `attention_hook.py:574` | `conditionalization_marginal_available = False`（硬编码 + 原因） |
| `tests/test_attention_hook.py:333` | 锚点测试断言该值为 `False` |

### 5.3 三条合取项的现状（建议做成三色进度条）

| 合取项 | 量具/链路 | 缺什么 | 结构上可测吗 |
|---|---|---|---|
| ③ prefill 加速 ≥1.10× | ✅ 已接 | **真权重 + 真实运行**（给卡就能出数） | ✅ 是 |
| ① 与 dense 非劣 | ✅ 判定程序就位 | **两个参数**（给参数就能判） | ✅ 是 |
| ② 质量提升 ≥1.5pp | ✅ 链路闭合 | **真实多设备路径**（硬门槛） | ❌ **单卡恒 ≈ 0** |

> 💡 讲法建议：把 ①③ 说成"**只缺跑一次 / 只缺两个参数**"，把 ② 说成
> "**缺的是前提条件本身** —— 不给真多卡，给多少时间都测不出来"。
> 这个区分是本页最有说服力的地方。

### 5.4 门槛清单（要判 H2 必须先满足）

| 条件 | 内容 |
|---|---|
| A（硬门槛） | ≥2 张 GPU；`--ranks > 1` 且真的起进程组（脚本有闸门，防"声明多卡实际单卡"） |

## 6. 成果三、四：评测方法论（3–4 页，**本汇报技术含量最高的部分**）

### 6.1 起点：发现旧评测集"测不出东西"

端到端四臂全部 `acc = 1.0000`。**看起来像"压缩不掉点"，实际是零区分度**：

```
参照臂（dense）准确率 = 1.0000   ← 已满分，只能测出下降、测不出提升
配对不一致对总数 = 0             ← 配对检验（McNemar）功效为零
```

⇒ 这份评测集**只能**支持"链路跑通"，**不能**支持"精度不降"。

### 6.2 动手：新建两支探针

| 探针 | 性质 | 为什么敏感 |
|---|---|---|
| **NIAH**（Needle-in-a-Haystack） | 合成探针 | needle 全上下文**只出现一次**，压掉即答错 ⇒ 对压缩天然敏感 |
| **LongBench** `passage_retrieval_zh` | 真实任务 | 答案形如「段落N」，可 100% 定位 |

**结果**：配对不一致对 **从 0 增至 10**（NIAH 侧）。

### 6.3 主结果：NIAH n=20（**建议做成核心柱状图**）

| 臂 | acc (n=20) | 与 dense 的不一致对 | 真裁了吗 |
|---|---|---|---|
| `dense` | **1.0000** | — | — |
| `stride_0.25` | **1.0000** | 0 | ✅ 768→192 |
| `rand_0.25` | 0.9500 | 1 | ✅ 768→192 |
| `topk_0.5` | 0.4500 | 11 | ✅ 768→384 |
| `topk_0.25` | **0.2500** | 15 | ✅ 768→192 |

**配色建议（中国股市惯例）**：`dense`/`stride` 用灰色基线，`topk` 两档用**红色**（劣），
`rand` 用橙色（接近基线）。**不要**用绿色表示"好"。

**配对 McNemar（精确，双尾）**：

| 比较 | b | c | p | 判定 |
|---|---|---|---|---|
| topk_0.25 vs rand_0.25 | **0** | 14 | **0.0001** | 显著 |
| topk_0.25 vs stride_0.25 | **0** | 15 | **0.0001** | 显著 |
| topk_0.5 vs rand_0.25 | **0** | 10 | **0.0020** | 显著 |
| rand_0.25 vs stride_0.25 | 0 | 1 | 1.0000 | 不显著 |
| topk_0.5 vs topk_0.25 | 4 | 0 | 0.1250 | 不显著 |

**两条核心读法（务必分别成句）**：
1. **`b = 0` 比 p 值更硬** —— 20 条里**没有任何一条**出现「`topk` 答对而 `rand/stride` 答错」。
   不是"平均略差"，是**从头到尾没有一次反过来**。
2. **`topk` 的伤害在 50% 就基本到位**，再压到 25% 无额外显著恶化
   （`b=4, c=0, p=0.125`）。

### 6.4 本轮最漂亮的一条：**真裁 4× 却零损失**

⚠️ "满分"最可能是**根本没压**。所以做了**压缩自证**：每个压缩臂**独立复算 cache 实际长度**。

| 臂 | mode | 裁前 | 裁后 | `actually_cut` |
|---|---|---|---|---|
| `stride_0.25` | stride | 768 | **192** | ✅ true |
| `rand_0.25` | random | 768 | 192 | ✅ true |
| `topk_0.25` | topk_rms | 768 | 192 | ✅ true |

⇒ **`stride_0.25` 真裁掉 576/768（4×），仍 20/20 全对。**
**"压缩可以无损"在"别用 topk"的前提下成立。**

> 💡 这一页是全局最亮的点，建议单独成页并做视觉强调。

### 6.5 位置档拆解（NIAH 每档 5 条）

| 臂 | dst_local | src_head | src_mid | src_tail |
|---|---|---|---|---|
| `dense` | 1.000 | 1.000 | 1.000 | 1.000 |
| `stride_0.25` | 1.000 | 1.000 | 1.000 | 1.000 |
| `rand_0.25` | 0.800 | 1.000 | 1.000 | 1.000 |
| `topk_0.5` | 0.400 | 0.400 | 0.600 | 0.400 |
| `topk_0.25` | 0.200 | 0.400 | 0.400 | **0.000** |

**要点**：`topk_0.25` 在 `src_tail` 上 **5/5 全错**（最干净的一处退化）；
但伤害**不只集中在尾部**（`dst_local` 也掉到 0.200）⇒ **不要写成"只影响尾部"**。

### 6.6 阴性结果：LongBench n=20（**必须保留的一页**）

| 臂 | acc | 与 dense 不一致对 | 真裁了吗 |
|---|---|---|---|
| `dense` | **0.3000** | — | — |
| `topk_0.25` | **0.3000** | 6 | ✅ 768→192 |
| `rand_0.25` | 0.2500 | 3 | ✅ 768→192 |
| `stride_0.25` | **0.3000** | 2 | ✅ 768→192 |

**三对配对全部 `p = 1.0000`。**

**关键辨析（这是本页的价值所在）**：`topk` vs `dense` 是 **`b=3, c=3`** ——
压缩把 3 条由对变错，**同时把另外 3 条由错变对**。**总量不变、成员互换。**

⇒ 这是**无分辨力仪器**的特征（有变动，但方向不由被测操作决定），
**不是**"被测量为零"的特征。

叠加决定性旁证：**同模型、同预算、同模式**，NIAH 上 `b=0, c=15, p=0.0001` ——
一支单向崩塌、一支完全测不出 ⇒ 更合理的解读是**该探针在本规模上无分辨力**。

> ⚠️ 这仍是**证据权衡**，不是演绎证明：无法排除"该任务恰好对这个压缩不敏感"。
> **两种解释都写进报告，不替读者下判。**

## 7. 自我纠正：我们推翻了自己的结论（1–2 页，**严谨性亮点**）

### 7.1 被推翻的那条

| 阶段 | 观察 | 当时的结论 |
|---|---|---|
| n=8 | LongBench 上 `topk`(0.250) > `rand`(0.125)，与 NIAH 相反 | 写成「**本节最重要的结论**」，推出"次序依探针而定" |
| **n=20** | `topk` 0.300 vs `rand` 0.250，**p=1.0000，并排** | **翻转消失 ⇒ 那个次序是 n=8 的噪声** |

**处置方式**：旧报告**原文保留不动**（它是"这结论当初为什么被写出来"的证据）
＋ 顶部加 `⚠️ 已被 <新报告> 修正`；相关报告的"待补"节改写为「已完成，答案：**不成立**」。

### 7.2 从中提炼的两条纪律（本页是全汇报的思想内核）

1. **`arm ≈ dense` 有两种成因，不可混读**：
   ①操作真无害；②**仪器分辨不出**。
   区分判据：看不一致对的**方向** —— **总量不变、成员互换（b≈c）＝分辨力不足**；
   **单向（b=0 或 c=0）＝真效应**。
2. **小编号（n≤8）下的序关系一律不当现象**，只当"待扩充的线索"。

### 7.3 顺手抓出的一个自身缺陷

实现判据时，最初把分辨率读数命名为 `ci_halfwidth_pp` 并当"置信区间"用 —— **错的**。
反例：`b=0, c=4, n=20` 时读数 `19.6 pp < |Δ| = 20 pp`（**看着显著**），
而**精确 McNemar `p = 0.125`，不显著**。

⇒ 已改名 `resolution_halfwidth_pp`，明写「**不是可推断区间，推断一律以 `p_value` 为准**」，
并把反例**固化成测试**。

| ❌ 声称**已与基线对比**（`fastkv_official` / `ring` / `apb`） | 这三条基线被阻断（`--plan` 输出 3/6 被阻断） |
| ❌ 把 `hook_dcc` 的耗时当"压缩收益/损失" | 那是 `prefill_speedup_native` 口径，含实现差距 |
| ❌ 用"压缩无损"概括 LongBench 结果 | 只能报"**该探针测不出**"，两者不是一回事 |

### 8.2 必须带上的限定语

| 陈述 | 必须带上 |
|---|---|
| NIAH 的相关结论 | 「**仅在本探针、本模型（Qwen2.5-0.5B）、本预算档上成立**」 |
| 跨族挂载可行 | 「这是 **0.5B**，**不可**外推为 72B 同样可行」 |
| "未检出差异" | 「在**探针尺度 25 pp** 下可报'未检出 >25pp 的退化'；**论文尺度 1.5 pp 下什么都报不了**」 |
| 4k 长文本 | 「论文的 4096 是 **GPU + 8B**；本次是 **CPU + 0.5B**，**量纲不可互推**」 |
| 压缩机制 | 「源自 **MIT CSAIL Attention Matching（arXiv 2602.16284）**，**非本项目原创**」 |

### 8.3 一处必须说明的勘误（**若 PPT 里出现 `budget_0.5` / `budget_0.25` 行**）

这两个臂的**标签是错的**：它们实际传的是 `compaction_mode="identity"`，
而该模式在实现里是「**裁剪策略 = 恒等**」⇒ **什么都没裁，实际等于 `dense`**。
实测：`identity` 裁后 cache 长度仍是 **3072**；只有 `topk_rms`/`random`/`stride` 才裁到 **768**。

⇒ 那批 `acc=1.0000` **不构成"压缩后仍正确"的证据**。
**有效模式只有 `topk_rms` / `topk_norm` / `random` / `stride`。**

## 11. 本阶段结论与下一步（结尾页素材）

### 11.1 本阶段可主张的（有落盘证据）

- 真模型 + 真注意力类上**链路跑通**（含 4k 长文本、源端切 2/4 段）；
- **跨族零改动**挂载成功（0.5B 范围内）；
- 切分→多进程→归并**机制可跑**；归并数学正确（隔离对照误差 ≈ 3e-7，不随 N 累积）；
- **评测集区分度从 0 提升到 10 个配对不一致对**；
- **量具判据落成**：单一事实源 + 29 项锚点，全库 **525 项测试无回归**。

### 11.2 本阶段**不能**主张的

任务质量、通信性能、多卡可扩展性、与基线的对比。

### 11.3 下一步（按依赖顺序，**第 1 步是硬前提**）

1. **拿到 ≥2 张 GPU** → 跑 `dcc_kv` 与 `kv_budget_shared` 的真多卡对照行；
   （在此之前，第 2、3 步做了也没用 —— 因为质量差恒 ≈ 0）
2. **声明两个统计参数** `--h2-delta-pp` / `--h2-noise-floor-pp`（先做一次重复 run 测噪声底线）；
3. **补干净对照臂** —— `budget=chunk` 是**伪对照**（关不掉压缩链路），
   唯一干净基准是 `blockwise_no_compression`；
4. 提高评测分辨率（换更大模型 / 换任务档），使 LongBench 侧具备分辨力。

## 12. 术语小抄（制作方遇到生词查这里）

| 术语 | 人话解释 |
|---|---|
| **KV Cache** | 大模型推理时缓存的历史键值对，随序列长度线性增长，是长上下文的主要瓶颈 |
| **dense** | 基线臂：不压缩，走标准精确注意力 |
| **topk / rand / stride** | 三种"选哪些 KV 留下"的策略：按重要性打分取前 k、随机、等间隔 |
| **配对 McNemar** | 同一批题目上比较两个方法，只看"不一致的那些题"，统计上比单纯比准确率更灵敏 |
| **b / c** | 配对检验的两类翻转计数：b = 前者对/后者错，c = 反之 |
| **不一致对** | `b + c`，即两个方法答案不同的题目数。**它是"评测集能不能测出差异"的衡量** |
| **NIAH** | 大海捞针：把一根"针"藏进长文，问模型针在哪。压掉即答错 ⇒ 对压缩敏感 |
| **LongBench** | 真实长文本评测集，本次用其中文段落检索子任务 |
| **H2** | 本项目要验证的核心假设之一：质量比共享压缩好 ≥1.5pp **且** 加速 ≥1.10× |
| **pp（百分点）** | percentage point，准确率从 80% 到 81% 就是 1 pp |
| **天花板效应** | 基线已满分，测不出向上空间，也测不出差异 |
| **O(S²)** | 注意力矩阵规模随序列长度平方增长 ⇒ 这就是"切分能省 W² 倍"的来源 |

## 13. 制作方备忘（做图时容易踩的坑）

1. **柱子高度按准确率画，但一定标出 `n=20`** —— 小样本不能给人"精确"的错觉。
2. **NIAH 与 LongBench 的数字不可放在同一张图上比较** —— 它们是不同题目、不同批次。
3. **"p=1.0000" 不要标成"两者相同"**，要标成"**这 20 条分不出**"。
4. **"b=0" 值得加粗**，它比 p 值更有说服力（一眼能懂：从没反过来过）。
5. 若空间允许，**§6.4 那张自证表**（裁前/裁后/actually_cut）建议用**对勾**视觉，
   它传递的是"我们验证过自己没作弊"。
6. **不要加进度百分比、不要加"预计完成度"** —— 这类数字项目里没有，编出来就是错的。
