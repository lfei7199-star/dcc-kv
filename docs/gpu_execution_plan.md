接上前的形态（原文保留 —— 它是这条缺口的证据，也是「量具失效长什么样」的标本）：
E6 的 `measure_point` 走 `_hf.measure_prefill`，而该函数的计时窗口里**只有一次
全长前向**，裁剪后的 KV 从未被任何前向使用（桩模型实测：4 次前向 input 恒为 S、
past 恒为 None）。于是对于任何压缩方法，

```
T_prefill(压缩) = 全长注意力耗时 + 压缩开销  >=  T_prefill(精确)
```

`prefill_speedup` **结构上恒 <= 1 < 1.10x**，H2 的第二个合取项永远不可能满足。
⇒ 那时把 `METHOD_SPECS["dcc_kv"]["measurable"]` 直接翻成 `True` 会得到一个
**确定性的假阴性**（「压缩不加速 prefill」），而根源是量具，不是方法。

**接上后（现行为，2026-09-21）** —— `_one()` 做三件事，缺一不可：

```
① 源端构造  lm.model(src_ids, use_cache=True)          <- 两臂共有，不可被压缩降低
② 压缩      apply_kv_budget(cache, B)                  <- 仅压缩臂
③ 目的端    lm.model(dst_ids, past_key_values=cache)   <- H0 的收益载体
```

③ 看到的 KV 长度：dense 臂是 S、压缩臂是 B，**其余全同** ⇒ 加速比的差别只能来自
这里。压缩臂不给 `dest_len` 会直接抛 `ValueError`（堵住「忘了开 ③」这条静默失效
通路 —— 那正是此前 `PREFILL_TIMING_CONSUMES_COMPACT_KV` 为 `False` 的原因）。
常量随之翻为 `True`；E6 新增 `--dest-fraction`（默认 0.25），落进每行产物与
`instrument` 块。

**但 H0 修的是量具，不是方法实现。** 翻 `measurable` 仍然不可以，原因不是量具
（已修），而是 `measure_point` 里这两行：

```python
budget_ratio = None if method == "dense" else a.budget_ratio
mode = "identity" if method == "dense" else a.compaction_mode
```

`dcc_kv` 与 `kv_budget_shared` 因此**走的是同一条 `apply_kv_budget`（共享裁剪）
路径** —— 没有目的端条件化构造，也没有 G2 的 `pipelined_attention`。两者的质量差
会**恒为 0**，H2 的 `quality_gain` 无从谈起。此时翻 `measurable` 会让 H2 拿一条
**不是本文方法**的通路去判质量臂：那不再是假阴性，而是**假阳性**，更坏。
**能翻 `measurable` 的充要条件**：`dcc_kv` 在 `measure_point` 里走 G2 的
`pipelined_attention`，而不是与 `kv_budget_shared` 同一分支。

阻断原因全部是**实现缺口**，与租什么卡无关：

## 1. 为什么「先租卡、再补代码」是最贵的顺序

三条理由，按代价从大到小：

**① 多卡小时单价最高，而多卡要跑的实验恰恰阻断最多。**
只有 E5 需要 ≥2 卡（NCCL）。E5 的四个部件里：A3 死于 G1、A4 死于 G4、
A2 要真实模型加评测集、只剩 A1 和 A5 是 synthetic 后端可跑。
**为两个通信计时测量去租 4×A100，是这份计划里最贵的一笔浪费。**

**② 第一次上机必然暴露问题，而暴露问题的成本 = 当时的机器单价。**
本机无 CUDA，`src/dcc_kv_ref` 下那三处 device 修复（`representative_query.py`、
`value_regression.py`、`key_selection.py:49`）目前**只是静态审计结论**。
`_env.probe_gpu_construction()` 在真机上可能通过、也可能不通过。
把这次未知安排在 1 卡上，成本是安排在 4 卡上的四分之一。

**③ 计时数据的可信度依赖「先小规模校准」。**
`--iters` 低于 10 时脚本会警告（§6.1 要求每点 ≥10 次重复）。全量跑之前必须先用
小 `--iters` 跑通一轮测出单点实际耗时，再外推总时长。跳过这步等于盲目烧钱。

## 3. 预算控制纪律

1. **先补代码，后租多卡。** 多卡单价最高，留给已经跑通验证的实验。
2. **1 卡起租，绝不上来就 4 卡。** S1 的探路成本应当是整轮里最低的一笔。
3. **每阶段设终止判据**（见 S1），失败即停，不"顺便再跑跑看"。
4. **先小 `--iters` 冒烟，再全量。** 用冒烟测出的单点耗时 × 点数外推预算，
   而不是凭感觉估。
5. **不要用 8×H100 跑 8B。** `reproducibility.md` §4 里 8×H100 只对应
   70B/72B —— 而**70B/72B 目前根本没有对应脚本**（G3 之外的又一缺口）。
   E6 的 3 个模型全是 7B/8B 量级。
6. **`--build-location auto` 若退化为 CPU 构造，`T_build` 会含 PCIe 传输。**
   这种 run 的计时不可与 GPU 构造的 run 混报，报告里必须声明。
7. **`--iters` 不得为了省钱降到 10 以下**（§6.1 硬要求）。要省时间就减点数，
   不要减重复次数。
8. **一次把 `--out` 写全。** GPU 单次 run 规划 1–100 MB，中途断线重跑比按时长付费更亏。
9. **计时窗口内不得出现集合通信**（`run_sync_pipeline` / `run_async_pipeline`
   内部只用 `device_sync()`）。异步版若在 `handle.wait()` 后再做一次 device-wide
   同步，会连正在飞的下一块一起等掉，overlap 恒为 0、加速比恒为 1.0 ——
   这种 run 会白花一整天。
10. **产物必须落盘到 `results/gpu/**` 并随仓库提交**（D3 裁决），
    否则租卡买来的数据在下一次会话里就找不回来了。

## 4. 数据量与前向次数估算

### 4.1 网格规模（取自脚本默认实参，非估）

| 实验 | 网格 | 数据点 | 每点 run | 总前向/操作数 | 卡数 |
|---|---|---|---|---|---|
| **E8** | dtype 2 × `--num-blocks` 多档 × tree 3 × `n_perms` 20 | ~600 次归并 | — | ~600 | 1 |
| **E6（可测）** | 2 方法 × 3 模型 × 4 长度 | 24 | ≥10 | **240** | 1 |
| **E6（全量，补齐后）** | 6 方法（按各自轴累加） | 120 | ≥10 | **≥1200** | 1–2 |
| **E7** | 4 条件（short_ctx 3 档 / low_budget 3 档 / retrieval 若干 / batch1 4 档） | ~13+ | ≥10 | ~130+ | 1 |
| **E5-A1** | `--blocks-per-rank` 4 档 × 同步模式 | ~8 | ≥10 | ~80 | 2–4 |
| **E5-A2** | `--budget-ratios` 5 档 × 模型 × 评测集 | 5+ | ≥10 | ~50+ | 2–4 |
| **E5-A5** | `--chunks` 4 × {sync, async} | 8 | ≥10 | ~80 | 2–4 |

> E6 的 120 点是**按各方法自身的轴累加**得来的（`sync`/`async` 轴对
> `dense` / `kv_budget_shared` 折叠），不是 6 个数字简单相乘。
> 这与论文 §6.4 的 144 既不同值也不同义，**不要把脚本总数当成论文声称的数据点数**。

### 4.2 时长粗估（**估算，必须用 S1 的实测值替换**）

估法：单次 prefill 的浮点量 ≈ `2 × P × L`（P 为参数量，L 为上下文长度），
再除以有效算力（A100 bf16 按 150 TFLOPS 计，已含效率损耗）。

对 8B 模型、batch=1：

| 上下文长度 | 单次 prefill 估算 |
|---|---|
| 4096 | ~0.6 s |
| 8192 | ~1.2 s |
| 16384 | ~2.4 s |
| 32768 | ~4.8 s |
| **四档合计** | **~9 s** |

据此外推：

| 实验 | 粗估（单卡） |
|---|---|
| E8 全量 | < 5 分钟（纯算子，无模型） |
| E6 可测部分（240 前向 × 3 模型） | **~20–40 分钟**（含 3 次模型加载各 1–2 分钟） |
| E7 全量 | ~30–60 分钟 |

> **这些数字的作用是给「第一笔钱该充多少」一个量级判断，不是预算承诺。**
> 三个不确定源：打分阶段每个选项各需一次前向（可能使实际翻倍）、
> 模型加载受磁盘带宽支配、压缩构造的额外开销未计入。
> **上机第一件事是跑单点实测，用它替换本表。**

**结论：S1 + S2 两阶段（单卡）合起来是一个「几小时」量级的开销。**
真正的大额支出是 S3 的多卡，而 S3 有四项前置缺口未补齐 —— 所以现在**没有**
需要大额预算的事项。
